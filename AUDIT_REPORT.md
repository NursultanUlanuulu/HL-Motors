# Аудит безопасности и QA — Motors

**Дата:** 14–15 сентября 2026. **Ветка:** `codex/security-qa-audit`. **Исходный commit:** `d2070c25b70443bb24883bff6c4f0b0552a528cb`.

**Решение: публичный выпуск в проверенной конфигурации заблокирован.** Пустой `ADMIN_PASSWORD` включает известный пароль администратора; выход не отзывает токен; API сохраняет некорректный тип поля, который ломает публичную страницу. Успешные штатные тесты эти проблемы не обнаруживают.

Аудит выполнен, основной код не исправлялся. Найдено 9 подтверждённых проблем разной серьёзности; подтверждение имеет явно указанную границу: HTTP/браузер, SQL или отдельный модуль. Подозрения на поведение настоящего Supabase не включены в число подтверждённых уязвимостей.

## Окружение и границы доказательств

- Рабочее дерево перед аудитом было чистым; создана отдельная ветка. Изменения добавлены только в этот отчёт и `tests/audit`. Исходники, миграция, настройки и зависимости приложения сохранены.
- Node `24.13.1`, Next `16.3.5`, React/React DOM `19.2.0`, Supabase JS `2.116.0`, TypeScript `5.9.3`. Реальные версии и метаданные: [inspection.json](tests/audit/evidence/inspection.json).
- Production-сборка запускалась локально на порту 3107 с **явно переопределёнными** `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `ADMIN_SESSION_SECRET`, `ADMIN_PASSWORD`. Существующая внешняя база из `.env.local` не использовалась. Определено только наличие переменных; секреты не публиковались. `ADMIN_PASSWORD` в имеющемся файле пуст.
- БД: новый **PGlite PostgreSQL в памяти**, без внешнего адреса и без реальных записей. Точная миграция репозитория применена после создания тестовых ролей и заглушки таблицы `storage.buckets`. Все автомобильные записи, новые контакты и токены синтетические.
- Между приложением и БД — ограниченный локальный HTTP-адаптер PostgREST на `127.0.0.1:54329`. SQL, ограничения, триггер и изменения данных реальны; реализация PostgREST — тестовая. Запросы адаптера выполняются привилегированным соединением, как серверный доступ приложения; запрет обычных ролей проверен отдельно через `SET ROLE`.
- **Настоящие Supabase Auth, JWT, Storage, подписанные загрузки и RLS через пользовательские REST-токены не запускались.** Docker, PostgreSQL CLI и Supabase CLI в PATH отсутствовали. PGlite не выдаётся за полноценную локальную установку Supabase.
- Edge/Playwright: 1440×1000 и 390×844. Внешние запросы браузера блокировались: шрифты, внешние фото, мессенджеры. Скриншоты поэтому подтверждают структуру/поведение, но не точное отображение внешних ресурсов.
- Активных запросов к production, рассылок и платежей не было. Доступ к npm использован только для advisory-проверки и установки изолированных инструментов аудита.

## Архитектура и критические сценарии

Next App Router: `/`, `/catalog`, `/catalog/[id]`, `/login`; `/admin`, `/admin/vehicles`, `/admin/settings`, `/admin/analytics`, `/admin/contacts`. API: публичный `GET /api/site`; административные `POST/DELETE /api/admin/vehicles`, `POST /api/admin/contacts`, `POST /api/admin/media`. Server Actions: login, logout, ensureAdminSession.

Единственный администратор `admin`, HMAC-cookie на 12 часов; собственная авторизация, Supabase Auth не используется. Организаций, обычных зарегистрированных пользователей, заказов, оплаты, подписок, восстановления пароля и одноразовых ссылок в приложении нет. Поэтому классический IDOR между аккаунтами/организациями здесь неприменим: посетитель читает общий публичный каталог, администратор управляет всеми машинами.

`vehicles`: ID, JSONB `data`, версия, timestamps; `site_settings`: контакты. Запись машины использует версию в SQL-предикате, изменение контактов — сравнение предыдущего JSONB. `vehicle-media` публичный по назначению; сервер выдаёт случайные пути для загрузки. В локальном режиме каталог/контакты находятся в localStorage, медиа — IndexedDB, и не являются общими для разных устройств.

Проверенные критические сценарии: вход/выход, CRUD объявлений прямым API, повтор запроса, конкурентное изменение/удаление, изменение контактов через UI и API, две вкладки, потеря сети, утрата сессии, прямые ссылки, reload/back, RU/CN, отказы upstream, пагинация в имеющихся тестах и ограниченная нагрузка.

## Подтверждённые находки

### F01. Известный пароль включается в production

**Условия/роль:** посетитель без сессии; `ADMIN_PASSWORD` отсутствует или пуст. Именно пустое значение обнаружено в текущей локальной конфигурации. **Файлы:** `lib/admin-auth.ts:18`, `app/actions/auth.ts:7`, `.env.example`, `SUPABASE_SETUP.md`.

**Воспроизведение:** `node tests/audit/prepare.cjs`, затем `node tests/audit/run.cjs`; открыть `/login`, ввести `admin` и fallback-пароль из `validCredentials`. Скрипт выполняет настоящий вход через форму production-сборки.

**Ожидалось:** административный вход отключён до задания индивидуального пароля. **Фактически:** переход на `/admin/vehicles`, cookie `HttpOnly=true, Secure=true, SameSite=Lax`, срок около 43200 секунд. После входа подтверждена запись синтетических автомобилей в БД.

**Доказательство:** `results.json` → `default admin password grants actual production session` и `persisted create, replay, concurrent update and delete integrity`. Токен не записан в отчёт. **Последствия:** полный контроль каталога, контактов и разрешений на загрузку медиа любым знающим fallback-пароль.

**Минимальное исправление:** убрать fallback, требовать непустой сильный пароль до запуска административных функций; поправить пример и инструкцию, называющие пароль необязательным. **Регрессия:** при пустой переменной login отвергает вход и не выдаёт cookie; индивидуальный пароль работает, прежний fallback — нет. Использовать настоящую `validCredentials`, а не mock `isAdmin`.

### F02. Выход и смена пароля не отзывают выданные сессии

**Условия/роль:** держатель ранее действительной cookie администратора; знание ключа HMAC не требуется. Само похищение cookie не исследовалось. **Файлы:** `app/actions/auth.ts:17`, `lib/admin-auth.ts:27`.

**Шаги:** войти; сохранить cookie только в памяти теста; нажать «Выйти»; повторить `POST /api/admin/vehicles` с прежней cookie и правильным Origin. Отдельный модульный опыт меняет ADMIN_PASSWORD после создания токена.

**Ожидалось:** отозванная сессия даёт 401 и ничего не записывает. **Фактически:** браузерная cookie удалена; запрос без неё даёт 401; воспроизведение старой cookie даёт **200**, в PostgreSQL появляется `AUDIT-LOGOUT`, версия 1. После смены пароля старый пароль уже неверен, но прежний токен всё ещё принимается.

**Доказательство:** `results.json` → `logout deletes browser cookie but replay still writes to database`; [local-probes.json](tests/audit/evidence/local-probes.json). **Последствия:** выход/смена пароля не прекращают доступ держателя копии токена, до истечения 12 часов или смены общего секрета.

**Исправление:** серверные записи сессий с отозванным состоянием либо проверяемая версия сессий пользователя; logout отзывает конкретную сессию, смена пароля — все сессии. **Регрессия:** настоящий login → logout → replay → 401, ноль новых записей; аналогично после смены пароля. Cookie-флаги уже выставляются корректно.

### F03. Нестрогая схема допускает данные, ломающие отображение

**Условия/роль:** администратор через прямой API или некорректный импорт. Это не повышение роли обычного пользователя. **Файлы:** `lib/site-data.ts:8`, `lib/cloud-validation.ts:17`, `lib/cloud-repository.ts:8`, `lib/i18n.ts:8`, `components/VehicleDetail.tsx:28`.

**Шаги:** взять `synthetic('AUDIT-TYPE')` из harness, установить `condition: ['Новый']`, отправить `{car}` на `/api/admin/vehicles`; затем открыть `/catalog/AUDIT-TYPE` на RU. Отдельно добавить неизвестные поля `owner_id`, `role`, `internal_note: 'AUDIT_PRIVATE_MARKER'` и прочитать `/api/site` без cookie.

**Ожидалось:** массив вместо enum-строки отклоняется с 400 до записи; неизвестные/служебные поля отклоняются или удаляются, публичная проекция содержит только явно разрешённые поля. **Фактически:** POST 200, массив хранится в JSONB. Браузер получает `.replace is not a function` и экран «This page couldn’t load». `String(car.condition)` позволяет массиву пройти проверку. Публичный API также возвращает весь `internal_note`; поля `role/owner_id` сохраняются, но сами по себе прав не дают.

**Другие симптомы той же неполной валидации:** `status: ['В наличии']` проходит JS-проверку, затем отвергается SQL и выдаёт 503; JSON-body `null` вызывает 503 вместо клиентской ошибки. Некорректный запрос ошибочно выглядит как отказ Supabase.

**Доказательство:** `results.json` → `enum arrays...`, `public rendering crashes...`, `input boundaries...`; [скриншот](tests/audit/evidence/invalid-condition-crash.png). Падение карточки подтверждено браузером; аналогичный вызов `t(car.condition)` присутствует в списке, но отдельный браузерный crash списка не измерялся.

**Последствия:** сохранённая некорректная запись ломает просмотр; произвольные непубличные поля импорта могут оказаться в публичном API. Реальная утечка пользовательских данных не проверялась и не утверждается.

**Исправление:** строгая схема JSON-body и Car с проверкой `typeof` enum-полей, явным набором разрешённых ключей и публичным DTO; дополнительная валидация данных при чтении с локальной изоляцией повреждённой карточки. **Регрессия:** массивы/null/unknown fields → 400 без новых строк; валидные RU/CN записи → 200; неправильная запись не должна уронить весь экран; публичный ответ не содержит тестового internal_note.

### F04. Правильный Origin по IP отвергается

**Условия:** локальная сборка открыта как `http://127.0.0.1:3107`. **Файл:** `lib/api-server.ts:7`; Next `dist/server/web/next-url.js` нормализует loopback-адреса в `localhost`.

**Шаги:** POST `/api/admin/vehicles` на IP с `Origin: http://127.0.0.1:3107`; повторить на `http://localhost:3107` с соответствующим Origin. **Ожидалось:** одинаковый переход к проверке сессии. **Фактически:** IP получает 403 «Недопустимый источник запроса», localhost без cookie — 401. Первый запуск также воспроизвёл 403 после успешного входа по IP для корректных операций записи.

**Доказательство:** `results.json` → `loopback IP origin...`; [initial-origin-run.json](tests/audit/evidence/initial-origin-run.json). **Последствия:** вход работает, но сохранение/удаление/подписание загрузок по IP не работают. Поведение за production-прокси не проверено.

**Исправление:** сравнивать Origin с явно настроенным списком допустимых внешних origin; корректно учитывать документированную нормализацию и доверенный прокси. Не принимать произвольный подставленный Host/X-Forwarded-Host. **Регрессия:** настоящий NextRequest на разрешённых localhost/IP/домене проходит к auth, посторонний Origin остаётся 403. Существующий тест с обычным `Request` этого не видит.

### F05. Ограничения JSONB допускают отсутствие обязательных ключей

**Условия/роль:** привилегированный SQL-писатель/миграция/будущий обход валидатора, не публичный пользователь. **Файл:** `supabase/migrations/202609140001_catalog.sql:10`.

**Шаг:** в новой изолированной БД выполнить `INSERT INTO vehicles(id,data) VALUES ('AUDIT-INVALID-SQL','{}');`. **Ожидалось:** отказ CHECK из-за отсутствия id, price, status. **Фактически:** PostgreSQL сохраняет `{id:'AUDIT-INVALID-SQL', data:{}, version:1}`: выражения с отсутствующими JSON-ключами дают NULL, который удовлетворяет CHECK.

**Доказательство:** `results.json` → `migration CHECK constraints...`; после измерения тестовая строка удалена. **Последствия:** БД не обеспечивает заявленные обязательные поля; возможны неисправимые UI-записи от привилегированного импортера. Проверенный публичный API `{}` отвергает.

**Исправление:** требовать наличие ключей и корректные JSON-типы; использовать NOT NULL-эквивалентные проверки для выражений, а не только сравнения. **Регрессия:** выполнить настоящие INSERT/UPDATE `{}`, отсутствующих ключей, JSON null, некорректных типов и отрицательной цены; каждый должен отклоняться SQL, валидный документ — сохраняться.

### F06. Попытки входа не ограничиваются приложением

**Условия/роль:** любой посетитель. **Файлы:** `app/actions/auth.ts:7`, `lib/admin-auth.ts:18`. В исходниках нет счётчика, блокировки или задержки.

**Шаги:** записать формат настоящего login-запроса, заменить тестовый пароль на заведомо неверный, выполнить максимум 12 запросов последовательно за 10 секунд. **Ожидалось:** защита после заданного порога либо явно настроенный внешний limiter. **Фактически:** все 12 немедленно обрабатываются с HTTP 200 и сообщением неверного пароля, примерно за 0,1 секунды. 200 здесь — ответ Server Action с ошибкой входа, не успешная аутентификация.

**Доказательство:** `results.json` → `bounded login failures...`. Подтверждён этот диапазон, а не бесконечное число попыток; внешняя защита хостинга не исследовалась. **Последствия:** возможность быстрого перебора единственной административной учётной записи.

**Исправление:** серверное ограничение по аккаунту и источнику с задержками/временной блокировкой, согласованное между экземплярами; предусмотреть восстановление, не создавая постоянный DoS блокировкой. **Регрессия:** после заданного числа неверных попыток дальнейшие запросы ограничены; после окна доступ восстанавливается, другой пользователь не блокируется глобально.

### F07. Неограниченная точность и величина цены нарушают представление

**Условия/роль:** администратор/импорт. **Файлы:** `lib/site-data.ts:13`, `lib/cars.ts:51`, `components/VehicleCard.tsx`, `styles.css`.

**Шаги:** сохранить автомобили с `price: 0.0001` и `price: 1e100`; открыть каталог. **Ожидалось:** согласованные правила валюты/диапазона, отсутствие нулевой отображаемой цены для положительной записи, устойчивый layout. **Фактически:** оба POST 200, PostgreSQL сохраняет значения; первое отображается как `$0`, второе выводит очень длинное число и растягивает страницу. На ширине 390 px нормальный каталог имеет scrollWidth 390, с граничными данными — горизонтальное переполнение. Отдельно `0.1+0.2` сохраняется как `0.30000000000000004`.

**Доказательство:** `results.json` → `small positive...`, `mobile catalogue...`, `mobile layout with normal prices...`; [скриншот](tests/audit/evidence/mobile-catalog.png).

**Последствия:** вводящая в заблуждение цена и неудобный публичный каталог. Финансовых транзакций нет; денежных потерь/ошибки списаний не утверждается. Максимальная цена и допустимость дробных USD в требованиях не определены.

**Исправление:** согласовать границы/точность цены, применять на сервере и в UI; хранить согласованную денежную единицу или decimal, ограничить переполнение текста. **Регрессия:** значения ниже минимальной единицы и выше максимума отвергаются; округление предсказуемо, валидные граничные цены не расширяют viewport.

### F08. Локальные контакты перезаписываются устаревшим снимком

**Условия:** локальный режим, два редактора одного браузера с прежним снимком контактов. **Файлы:** `lib/site-data.ts:80`, `components/SiteDataProvider.tsx:91`.

**Шаги:** прочитать контакты в две копии; первая меняет email и сохраняет; вторая меняет только Telegram и сохраняет старую копию с прежним email. **Ожидалось:** конфликт или сохранение обоих независимых изменений. **Фактически:** второе сохранение восстанавливает прежний email без ошибки.

**Доказательство:** `local-probes.json` → `local contacts lose another tabs email change`. Проверен настоящий модуль хранилища на детерминированном memory-localStorage; это не браузерный замер одновременного interleaving. В облачном режиме аналогичный сценарий двух настоящих вкладок корректно отвергается.

**Исправление:** учитывать предыдущий снимок и версию локальных контактов, сериализовать операции между вкладками, либо отключить локальный режим для совместной работы. **Регрессия:** две устаревшие копии не теряют первое изменение; ошибка сообщает о конфликте, сохранённое состояние проверяется повторным чтением.

### F09. Повторы upstream обходят общий ожидаемый бюджет таймаута

**Условия:** база принимает запрос, но не отвечает. Роль не нужна для `GET /api/site`. **Файлы:** `lib/supabase-server.ts:17`, `lib/cloud-client.ts:4`; установленный `@supabase/postgrest-js/src/fetchWithRetry.ts`.

**Шаги:** в локальном адаптере включить режим `timeout`, вызвать `/api/site`, измерить время до ответа. **Ожидалось:** конечный общий бюджет операции, близкий к объявленным в коде 20 секундам. **Фактически:** 503 только через **87 077 мс**. В итоговом опыте за это время адаптер принял 20 upstream-запросов суммарно, включая фоновое обновление открытой вкладки; это не число запросов одного вызова API. По реализации SDK один вызов делает две параллельные выборки с максимум четырьмя попытками каждой. Каждый fetch создаёт новый 20-секундный signal; TimeoutError допускает повторы SDK. Клиентский `apiRequest` собственного deadline не задаёт.

**Доказательство:** `results.json` → `outage and timeout...`; БД до/после не изменилась, диагностический маркер/секреты не раскрылись. Предварительный probe с 26-секундным клиентским deadline действительно оборвался раньше ответа; затем ожидание расширено для измерения реального поведения.

**Последствия:** долгие ожидания и удержание серверных запросов при отказе. Дополнительно по коду 30-секундный refresh меняет generation раньше завершения долгого запроса; возможное подавление сообщения об ошибке — **вывод по коду, не подтверждённый отдельным 87-секундным UI-опытом**.

**Исправление:** общий AbortSignal/deadline на операцию и согласованная retry-политика, не сбрасывать переданный signal каждой попыткой; конечный клиентский timeout и single-flight обновление. **Регрессия:** зависший upstream завершается в принятом бюджете, число попыток ограничено, UI выходит из ожидания и сохраняет последний успешный снимок с сообщением ошибки.

### Зависимости: advisory и применимость

Первый npm audit был заблокирован сетевым доступом; повтор с разрешённым доступом к registry завершился без advisory. Ноль advisory не доказывает отсутствие уязвимостей.

CVE-2025-55182 относится к пакетам `react-server-dom-*`, а не автоматически к корневому `react@19.2.0`. У Next `16.3.5` встроенный RSC указывает peer `19.3.0-canary-cbb046ab-20260731`; по одному номеру корневого React утверждать применимость старого CVE некорректно. RCE-exploit не запускался. Основания: [официальное описание React](https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components), [обновление Next.js](https://nextjs.org/blog/security-update-2025-12-11), установленный package.json. Проверка не является полным аудитом встроенного кода фреймворка.

## Подозрения и непроверенные области

1. **Storage:** сервер проверяет только заявленные `type/size`, а запрос подписи имеет body `{}`. Размер 15 МБ и сигнатура байтов не привязаны к выданной подписи на уровне приложения; бакет допускает 50 МБ для всех типов. Возможность отправить более крупное «фото», MIME spoofing, повторить upload token, изменить путь, прочитать/перезаписать чужой объект и исполнять загруженный контент требует настоящего Storage. Это не подтверждённый upload exploit. Публичные фото по самой модели данных не считаются утечкой.
2. **RLS/Auth:** проверены миграция и SQL grants в свежем PGlite. JWT обычных пользователей, anon REST-доступ, действующие policies/GRANTs production и реальное service_role-поведение Supabase не проверены. Утверждения о защите уже развёрнутого проекта недопустимы.
3. **Миграция существующей среды:** `CREATE TABLE IF NOT EXISTS` и `ON CONFLICT DO NOTHING` не исправят старые таблицы/настройки бакета; чужие ранее созданные policies не удаляются. Свежая схема проверена, upgrade из произвольного состояния — нет.
4. **Размер запросов:** `readJson` сначала полностью читает тело, потом считает JS-символы. Отклонение >256000 символов подтверждено; пиковая память больших/chunked тел и инфраструктурные лимиты не измерялись. Flood/исчерпание памяти не проводились.
5. **SSRF/paths/redirects/CORS:** пользовательские media URL отображаются браузером, явного серверного fetch по ним не найдено; Supabase URL берётся из server env. Выполнены отрицательные URL/ID-пробы, переадресации login/logout фиксированные. Произвольного исполнения, SQL injection, обхода путей или открытого redirect не подтверждено. Нет полноценного proxy/CDN/CORS-профиля deployment.
6. **Локальный режим:** проверены функции хранения и штатные tests; настоящий параллельный localStorage read-modify-write race и полный IndexedDB upload/reload/delete не воспроизводились. При отсутствии Supabase «опубликовано на сайте» означает данные данного браузера; внешнюю публикацию этот режим не обеспечивает и документация это описывает.
7. **Импорт/медиа:** по коду импорт частичный, повтор пропускает существующие ID; автоматического удаления облачных медиа нет, что документировано. Прерванный импорт с реальными файлами, очистка orphan-файлов, оборванная загрузка и фактические лимиты тарифа не проверены.
8. **Сбой после commit, до ответа:** таймаут после успешной записи, когда клиент не знает результата, отдельно не инжектировался. Повтор create и конкуренция проверены; frontend recovery после неизвестного результата требует отдельного теста.
9. **Полный e2e набор:** добавление/изменение/удаление машины подтверждено HTTP+SQL; через UI пройдены редактор и сохранение контактов, но не полный цикл заполнения машины/загрузки медиа/импорта. Мобильное меню, все браузеры, потеря сети непосредственно в upload, доступность из Китая и визуальная точность внешних шрифтов/фото не проверены.
10. **Неприменимо:** платежи, webhook, подписки, суммы заказов, tenant isolation, password reset, one-time links, даты бизнес-событий и экспорт отсутствуют. Тестовые SQL-принципы A/B не означают наличие пользовательских аккаунтов в продукте. Статические legacy HTML/JS не обслуживаются перечисленными Next routes; их отдельный deployment не запускался.
11. **Секреты/логирование:** проверены точные текущие секреты в текущих tracked-файлах/клиентской сборке и синтетические API-ошибки. Git history, реальные серверные логи, конфигурация reverse proxy, дампы/бэкапы и секреты других интеграций не исследовались.
