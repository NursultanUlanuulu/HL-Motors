# Воспроизводимый аудит

Приложение и его проверки не исправлены. Скрипты фиксируют и здоровое поведение, и существующие ошибки. `DONE` означает выполненную проверку, а **не отсутствие уязвимости**. Находки отмечены `finding`; `INCOMPLETE` означает, что сценарий не завершился.

## Запуск из корня репозитория

```powershell
npm ci --prefix tests/audit/runtime --no-audit --no-fund
node tests/audit/prepare.cjs
node tests/audit/run.cjs
node tests/audit/mutations.cjs
node tests/audit/local-probes.cjs
```

Нужны Node.js, установленные зависимости приложения и Microsoft Edge для Playwright (`channel: 'msedge'`). Исходная проверка: `npm test`, `npm run lint` (это только TypeScript, не ESLint), `npm run build`. Для безопасного повторного build используйте `prepare.cjs`: он явно переопределяет четыре переменные интеграции и не подключается к базе из `.env.local`.

`run.cjs` занимает примерно 2 минуты; проверка таймаута специально ждёт повторов SDK. Порты 3107 и 54329 должны быть свободны. Приложение слушает только loopback. PostgreSQL работает в памяти через PGlite; миграция применяется к новой БД без сетевого URL. Адаптер на 54329 поддерживает ограниченное подмножество PostgREST. Он не заменяет проверку настоящих Supabase JWT, PostgREST и Storage. `storage.buckets` и выдача upload URL — заглушки; реальные загрузки не выполняются.

Все активные запросы направлены на локальную тестовую сборку. В браузере заблокированы внешние шрифты, фото и ссылки на мессенджеры. Нагрузочная проверка: максимум 24 запроса, сначала 1, затем до 4 одновременно, дедлайн 15 секунд, остановка после первого 5xx; отдельная проверка входа — 12 заведомо неверных попыток, параллельность 1, до 10 секунд. Сценарии отказа БД выполняются отдельно от нагрузки.

Основные результаты: `evidence/results.json`, `evidence/run.log`, `evidence/local-probes.json`, `evidence/mutations.json`. Скриншоты сохраняются рядом. `initial-origin-run.*` сохраняют первый запуск с IP-адресом: ошибки 403 привели к отдельной находке F04. В текущем основном запуске используется `localhost`.

`mutations.cjs` создаёт временные копии исходников под `tests/audit`, меняет только их, запускает существующие 19 тестов и удаляет копии с проверкой пути. Контрольные SHA-256 подтверждают неизменность исходных файлов. Набор проверяет четыре конкретных мутации, не является полным mutation coverage.

## Точные примеры дефектов

- F01: при пустом `ADMIN_PASSWORD` войти через `/login` с `admin` и паролем по умолчанию из `lib/admin-auth.ts`.
- F02: сохранить тестовую cookie в памяти, выйти, повторить `POST /api/admin/vehicles` с прежней cookie и `Origin: http://localhost:3107`; запись принимается. Токены в лог не выводятся.
- F03: передать синтетический корректный `car`, заменив `condition` на `["Новый"]`. API возвращает 200 и БД хранит массив. Открыть `/catalog/<id>` на RU — исключение `.replace is not a function`.
- F04: тот же запрос на `http://127.0.0.1:3107` с соответствующим Origin возвращает 403; на `http://localhost:3107` Origin проходит проверку.
- F05: в изолированной БД выполнить `INSERT INTO vehicles(id,data) VALUES ('AUDIT-INVALID-SQL','{}');` — строка принимается вопреки назначению CHECK-ограничений.
- F06: 12 неверных попыток входа обрабатываются без задержки/блокировки. Это ограниченное доказательство отсутствия защиты на данном диапазоне; более высокие пороги не исследовались.
- F07: положительный `price: 0.0001` отображается как 0; `price: 1e100` сохраняется и растягивает страницу.
- F08: две устаревшие копии контактов в localStorage: второе сохранение восстанавливает старое значение поля, изменённого первым.
- F09: локальный upstream принимает соединение и не отвечает. Итоговый `/api/site` длится значительно дольше 20 секунд из-за повторов SDK.

После исправлений превратите наблюдения дефектов в регрессионные assertions ожидаемого безопасного поведения по `AUDIT_REPORT.md`. Сейчас некоторые проверки намеренно требуют наличие дефекта, чтобы его воспроизведение было проверяемым.
